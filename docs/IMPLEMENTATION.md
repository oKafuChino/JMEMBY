# JMEMBY 实现文档

状态：待开发。本文是开发 Agent 的执行依据，不代表相关功能或外部接口已经验证。

## 1. 项目目标

开发一个通过 Telegram Bot 管理漫画下载和入库的工具，部署在单台 Linux VPS 上，通过 Docker Compose 运行。

核心链路：用户提交禁漫漫画 ID 或受支持的链接 → 查看详情并确认 → 持久化排队 → 下载章节 → 生成 CBZ → 发布到漫画库 → Komga 扫描并确认入库 → Telegram 通知用户。

职责划分：

- JMEMBY：权限、下载任务、文件整理、入库协调、通知和运行状态。
- 数据源适配器：访问禁漫接口或第三方客户端，获取元数据、章节及图片。
- Komga：漫画索引、在线阅读、阅读进度和阅读用户管理。
- Docker Compose：服务编排、网络、持久化和重启策略。

第一版面向单管理员、单实例、单下载 worker。代码允许以后扩展，但不要提前引入分布式架构。

## 2. 范围与默认决策

### 2.1 MVP 必须实现

- Telegram 数字用户 ID 白名单；仅私聊；命令和按钮回调统一鉴权。
- 输入漫画 ID 或受支持链接，展示漫画详情，按钮确认后入队。
- 持久化任务、串行下载、可配置图片并发、任务查询和取消。
- 有限次数自动重试、手动重试、重启恢复。
- 以来源、漫画 ID 和章节 ID 去重。
- 下载图片、完整性校验、按章节打包 CBZ、发布完整文件。
- Komga 自动扫描、入库确认；下载成功与入库成功分别记录。
- Telegram 完成或失败通知；通知失败不改变下载结果。
- 磁盘阈值、临时文件管理、结构化日志、备份和恢复说明。
- 可重复构建的 Docker 镜像及 Compose 部署配置。

### 2.2 暂不实现

- 在线搜索、自动追更、订阅计费、多管理员分级、多用户配额。
- 独立 Web 管理界面、阅读器、Komga 用户账号同步。
- Redis、Celery、多 worker、多 VPS 调度。
- 自动删除已入库漫画、远程 shell、任意 URL 下载、自动升级依赖。

### 2.3 技术选型

| 项目 | 默认选择 |
| --- | --- |
| 应用语言 | Python 3.12；若数据源依赖不兼容，在技术验证记录中说明调整 |
| Telegram | aiogram 3，长轮询 |
| HTTP | httpx；使用现成客户端时沿用其受支持传输实现 |
| 配置 | pydantic-settings |

锁定验证过的依赖版本并提交锁文件。Komga 镜像固定版本，不使用 latest。初始下载 worker 数量为 1，图片并发建议为 2，并允许配置。

## 5. 模块结构与依赖边界

建议项目结构如下，允许小幅调整，但必须保留模块边界：

```text
src/jmemby/
  main.py
  config.py
  bot/                 命令、按钮、消息展示、鉴权中间件
  domain/              元数据模型、任务状态、错误类型
  services/            提交任务、取消、重试和入库编排
  providers/           数据源协议、禁漫适配器
  workers/             持久化调度、下载执行、恢复、通知补发
  storage/             路径规则、图片校验、CBZ、原子发布
  integrations/komga/   Komga HTTP 客户端及路径映射
  db/                  表模型、会话、查询和迁移
tests/
  unit/
  integration/
  fixtures/
docs/
Dockerfile
compose.yaml
.env.example
pyproject.toml
```

- Bot handler 只解析输入、调用 service 和呈现结果，不直接操作下载库或文件系统。
- 数据源适配器返回统一模型，不泄漏第三方对象到业务层。
- 下载器不发送 Telegram 消息；进度写入状态，由消息层限频展示。
- Komga 客户端不处理下载；扫描失败不能让下载器重复获取已完成图片。
- 文件路径由 storage 模块统一生成，不直接拼接用户输入或远端标题。

数据源协议至少覆盖：输入解析、漫画详情、章节清单、章节页清单、获取并还原图片。若所选客户端只提供整章下载，允许适配其调用粒度，但必须在适配层完成页序、校验、取消和错误转换。

统一错误分类：输入无效、内容不存在、鉴权失败、限流、网络暂时失败、图片损坏、磁盘不足、Komga 不可用和内部错误。错误应包含可公开的简短说明；原始响应不得直接发给用户。

## 6. 数据与状态设计

### 6.1 数据表

| 表 | 最少字段和约束 |
| --- | --- |
| manga | id、source、source_manga_id、title、authors、library_relative_dir、metadata_json；来源与漫画 ID 唯一 |
| chapters | id、manga_id、source_chapter_id、ordinal、title、expected_pages、relative_path、file_size、checksum、artifact_status、komga_book_id；manga_id 与来源章节 ID 唯一 |
| tasks | id、manga_id、requester_user_id、chat_id、status、phase、cancel_requested、retry_count、next_attempt_at、progress、error_code、safe_error、created_at、updated_at |
| task_chapters | task_id、chapter_id、status、attempt_count、downloaded_pages；任务与章节唯一 |
| notifications | id、task_id、event_type、status、attempt_count、next_attempt_at、message_id；任务与事件唯一 |

需要的关联表和索引可补充。全部时间以 UTC 保存。数据库文件置于持久化目录，开启外键、WAL 和合理的 busy timeout，使用短事务，不在网络请求期间持有事务。

同一来源漫画同一时间只允许一个未结束任务；用数据库约束或事务保证并发确认按钮不会产生重复任务，不能仅依赖内存检查。

### 6.2 任务状态

```text
QUEUED → DOWNLOADING → PACKAGING → IMPORT_PENDING → COMPLETED
             ↓             ↓              ↓
         RETRY_WAIT / PAUSED_DISK / FAILED
非终态任务 → CANCEL_REQUESTED → CANCELLED
```

- 多章节任务按章节循环下载与打包，任务 phase 表示当前活动；章节表记录真实产物状态。
- RETRY_WAIT 保存下次执行时间和恢复阶段；重试不长期占用 worker。
- PAUSED_DISK 等待磁盘恢复，展示暂停原因；周期性检查达到恢复阈值后重新排队，设置高于暂停阈值的恢复阈值以避免反复切换。
- IMPORT_PENDING 表示文件已发布但尚未确认 Komga 收录；扫描请求成功不能直接标记 COMPLETED。
- 只有所有目标章节文件有效且已确认入库，任务才能 COMPLETED。
- FAILED 保留已完成章节；手动重试创建关联的新任务，复用有效产物，只处理未完成部分。
- 任务提交时保存章节快照；运行期间新增章节留给以后再次提交，避免完成条件变化。
- 取消是协作式操作：等待当前可控操作停止后再标记 CANCELLED；已发布文件保留，明确告知用户。
- 手动取消后不自动重启该任务。终态转换与通知事件写入同一数据库事务。

### 6.3 去重与恢复

- 去重基于数据源 ID，不基于标题；同名漫画必须可以共存。
- 再次提交已完成漫画时核对章节及文件；全部齐全则直接返回已有结果，新增或缺失章节可建立补全任务。
- 启动时恢复中断任务：检查 staging、目标 CBZ 及章节记录，已校验发布的文件不重新下载。
- 处理“文件已发布但事务未提交”的崩溃窗口：根据稳定路径和 CBZ 完整性校验修复记录。
- 对存在但无效的目标文件报告异常，不静默覆盖或删除用户文件。
- 单实例部署应有进程锁或等效保护，第二个应用实例应明确拒绝启动，避免多个轮询器或下载器争抢任务。

## 7. 下载与文件发布

### 7.1 目录布局

```text
data/
  app/                         SQLite、迁移和应用状态
  komga/                       Komga 配置和数据库
  storage/
    staging/<task-id>/          图片、下载清单、临时 CBZ
    library/
      <清理后的漫画标题> [jm-<漫画ID>]/
        0001 - <章节标题> [<章节ID>].cbz
```

应用将 storage 整体挂载至 `/storage`，临时目录和最终目录位于同一文件系统。Komga 将宿主机 library 挂载至 `/data`。应用内 `/storage/library/A/B.cbz` 对应 Komga 内 `/data/A/B.cbz`；使用显式根路径映射，禁止简单替换任意字符串。

漫画和章节的路径首次生成后保存在数据库中，标题变更不自动重命名已入库文件。

### 7.2 处理步骤

1. 获取章节页清单，固定页序和预期页数。
2. 检查磁盘阈值及任务取消状态。
3. 将每张图片下载到 `.part` 文件；设置连接、读取和总操作时限。
4. 执行数据源要求的图片还原，验证实际图片格式、可解码性和大小限制。
5. 验证成功后保存为带固定宽度页码的文件，更新可恢复的清单。
6. 所有页完成后生成临时 CBZ，写入转义后的 ComicInfo.xml。
7. 检查 ZIP 完整性、图片数量和顺序、元数据内容；不接受空章节或占位文件。
8. 在同一文件系统内原子移动到目标路径；目标已存在时先核对，不无条件覆盖。
9. 更新章节产物记录，进入入库阶段。

CBZ 内图片使用诸如 `000001.jpg` 的页码名称，扩展名来自实际图像格式。图片通常已压缩，ZIP 使用低压缩级别或存储模式即可。元数据字段依据验证过的 ComicInfo 规范填充，包括漫画名、章节名、章节号、作者和页数。

### 7.3 资源与重试

- 可重试：网络超时、连接中断、部分 5xx、429、可恢复的图片下载错误。
- 不盲目重试：输入无效、内容不存在、持续鉴权失败、格式不支持。
- 尊重 Retry-After；使用指数退避和随机抖动，设置重试上限，避免客户端与外层重试相乘。
- 磁盘预算同时考虑原始图片、临时 CBZ 和已发布文件；未知大小不能宣称预算准确，应边写入边检查。
- 为单页字节数、图片像素数、章节页数和单任务体积设置可配置上限；超过限制给出明确失败原因。
- 临时文件清理只针对应用管理的 staging 子目录；活跃和可恢复任务不得被 TTL 清理。
- 收到 SIGTERM 后停止领取新任务，保存进度并在宽限期内退出；下次启动执行恢复检查。

## 8. Komga 入库流程

1. 启动时检查连接、鉴权、目标 library ID 和路径映射。
2. 发布完当前任务的所有章节后触发目标 library 扫描，避免逐页或逐文件扫描。
3. 使用有上限的轮询等待扫描结果，按照实际可用的路径/ID 查询方式确认目标书籍。
4. 全部找到后保存 Komga ID，标记 COMPLETED 并创建通知事件。
5. 扫描暂时不可用时保留 IMPORT_PENDING 或进入 RETRY_WAIT，后续仅重试入库。
6. 达到入库重试上限后标记 FAILED，错误说明必须包含“文件已保存，Komga 入库未确认”。

区分 `KOMGA_BASE_URL`（容器内请求地址）和 `KOMGA_PUBLIC_URL`（用户浏览器地址）。Telegram 消息不得输出 Docker 内部主机名。深链接无法验证时使用公共入口，不编造书籍 URL。

## 9. Telegram 交互

| 入口 | 行为 |
| --- | --- |
| `/start`、`/help` | 显示简要说明和命令 |
| `/download <ID或链接>` | 查询详情，显示确认/取消按钮 |
| 普通文本 ID 或受支持链接 | 与 download 相同 |
| `/queue` | 分页展示当前任务 |
| `/status <任务ID>` | 显示阶段、章节/页数进度、错误摘要 |
| `/cancel <任务ID>` | 请求取消；反馈是否已停止 |
| `/retry <任务ID>` | 为失败任务建立补全任务 |
| `/library` | 返回 Komga 公共访问入口 |
| `/disk` | 返回剩余空间、阈值及暂停情况 |

详情显示标题、作者、章节数和来源 ID；封面获取失败时仍可继续文本确认。按钮使用有过期时间的服务端待确认记录或签名数据，绑定发起用户和漫画 ID；重复点击应返回相同任务或已处理提示。

编辑同一条任务消息展示进度，默认最多每 5 秒更新一次；处理 Telegram 限流和消息已删除。对外部标题做 HTML/Markdown 转义。未授权请求不执行数据源查询，也不泄漏库状态。

终态通知持久化重试，但不得因通知发送失败重复下载。Telegram 发送与本地数据库之间不存在原子事务；消息编辑可减少重复，极端崩溃窗口允许重复终态提醒，不承诺严格恰好一次。

## 10. 配置与部署

### 10.1 必要配置

| 配置 | 说明 |
| --- | --- |
| TELEGRAM_BOT_TOKEN | 敏感配置，不记录到日志 |
| TELEGRAM_ALLOWED_USER_IDS | 数字 ID 列表；缺失或为空时拒绝启动 |
| DATABASE_URL | 默认指向持久化 app 目录的 SQLite |
| STORAGE_ROOT | 默认 `/storage` |
| KOMGA_BASE_URL | 容器内部访问地址 |
| KOMGA_PUBLIC_URL | 用户可访问的地址 |
| KOMGA_LIBRARY_ID | 预先创建的库 ID |
| KOMGA_LIBRARY_ROOT | Komga 容器中的库根路径，默认 `/data` |
| Komga 鉴权配置 | 根据验证过的版本选择一种方式，避免实现多套未经验证的机制 |
| 数据源鉴权配置 | 仅在所选客户端实际需要时提供 |
| DOWNLOAD_CONCURRENCY | 图片并发，默认 2；不代表多个任务并行 |
| RETRY_MAX_ATTEMPTS | 自动尝试总次数，默认 3，包含首次执行 |
| MIN_FREE_SPACE_GB | 暂停阈值，建议初始为 5 GiB，并明确单位 |
| RESUME_FREE_SPACE_GB | 恢复阈值，必须高于暂停阈值 |
| LOG_LEVEL | 默认 INFO |

其他时限、清理 TTL 和资源上限提供合理默认值并写入配置参考。`.env.example` 只有占位值；真实 `.env`、data 目录和下载产物加入 `.gitignore`。

### 10.2 容器要求

- app 使用非 root 用户，明确 UID/GID 与宿主机目录权限，不使用 chmod 777 解决问题。
- app 和 komga 通过内部网络通信；Bot 长轮询不暴露端口。
- Komga 默认端口仅绑定宿主机回环地址；公网访问通过单独配置的反向代理 HTTPS 或 VPN。
- Komga 配置目录可写，漫画库优先只读；如果实测功能要求可写，记录原因并调整。
- 配置重启策略、日志大小和轮转数量、停止宽限期；在目标 VPS 验证资源限制是否生效。
- 应用健康检查验证进程/事件循环和 worker 心跳；外部服务中断应显示为依赖异常，不制造无限重启。
- 数据库迁移在启动 worker 前完成；不兼容迁移失败时拒绝继续运行。

### 10.3 部署手册必须覆盖

准备持久化目录与权限 → 配置环境 → 启动 Komga → 在 Komga 完成初始账户和 library 设置 → 配置 library ID 与凭据 → 启动 app → 发送小任务验证 → 配置访问入口和备份。

升级前先备份数据库和配置。SQLite 使用在线备份 API 或停机一致性备份，不直接复制运行中的主数据库文件而忽略 WAL。Komga 数据按其版本文档备份；未验证在线备份时采用停机备份。说明恢复流程、文件路径保持要求，以及数据库迁移后旧镜像可能无法直接回滚。

## 11. 验证与验收

### 11.1 自动化检查

| 类别 | 必须覆盖的行为 |
| --- | --- |
| 权限/输入 | 未授权命令与回调拒绝；非白名单 URL 拒绝；按钮用户绑定和过期 |
| 路径/元数据 | 同名漫画、非法字符、目录穿越、超长标题、XML 转义 |
| 文件产物 | 页序、缺页、坏图片、正确 CBZ、半成品不出现在 library |
| 数据库 | 并发提交去重、状态合法性、任务快照、迁移 |
| 失败恢复 | 中断下载、发布后事务前崩溃、入库失败不重复下载 |
| 取消 | 排队取消、下载取消、底层执行停止、保留已发布章节 |
| 资源 | 磁盘不足暂停、恢复阈值、下载体积限制 |
| 外部集成边界 | 超时、429、5xx、鉴权错误、Komga 延迟索引、通知重试 |

离线测试用可控 fake provider、本地 HTTP stub、临时目录和真实 SQLite，避免真实账号与网络依赖。提供独立的显式启用集成测试，默认跳过需要真实凭据或下载内容的场景。

### 11.2 真实部署验收

- 白名单用户提交一个小漫画，确认后进入队列，Komga 可阅读全部目标章节，通知准确。
- 同一任务并发确认或重复提交，不产生重复文件或重复活动任务。
- 下载中重启 app，任务能够恢复或重新排队，已完成章节不重下。
- Komga 暂停时文件仍保存；恢复后只继续入库。
- 用户取消任务后底层下载停止，没有被误标为成功。
- 磁盘阈值被触发时暂停，释放空间后按配置恢复。
- 未授权用户、群聊和他人的按钮回调不能创建或操作任务。
- 删除进度消息或短暂断开 Telegram，不影响下载和入库结果。
- 重建容器后任务、漫画和 Komga 数据仍存在。
- 从备份恢复数据库和配置后，能够识别已有漫画并完成新任务。

真实验收记录写入 `docs/VALIDATION.md`，未执行项目标注“未验证”并说明依赖条件。

## 12. 实施里程碑

### M0：验证数据源和 Komga

产出：INTEGRATION_NOTES、依赖和镜像版本选择、章节映射与扫描策略。

验收：完成第 4 节；若外部条件缺失，明确哪些结论仍是假设。

### M1：项目骨架与持久化

实现：配置校验、日志脱敏、数据库模型和迁移、任务 service、单实例保护、fake provider。

验收：可建立并查询任务；并发提交不会产生重复活动任务；重启后数据仍在。

### M2：下载和文件管线

实现：禁漫适配器、下载、图片还原、页序校验、CBZ、路径生成、原子发布。

### M3：可靠任务执行

实现：队列领取、重试时间调度、协作取消、磁盘暂停、恢复协调、临时文件清理。

### M6：部署和交付

实现：Dockerfile、Compose、环境示例、CI 离线检查、README、部署/备份手册、验证记录。

验收：完成可执行的构建与配置检查，在具备授权及条件的环境执行真实部署验收，列明剩余未验证事项。

## 13. 完成定义

交付必须包含应用源码、迁移、锁文件、测试、镜像构建文件、Compose、配置示例、README、集成说明和验证记录。

核心完成条件：授权用户通过 Telegram 提交漫画，系统可恢复地下载并发布正确 CBZ，确认 Komga 入库后通知用户；重复提交、进程重启、外部服务短暂失败不会产生重复下载或虚假的成功状态。

如真实数据源或 VPS 未验证，交付应明确区分“离线实现与测试完成”和“真实集成验收完成”。
