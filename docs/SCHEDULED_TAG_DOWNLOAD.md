# 定时标签下载：实现流程与 Agent 开发指导

状态：本设计已落实为离线实现（2026-10-18）；真实集成待验收，见 [定时功能验收记录](SCHEDULE_VALIDATION.md)。以下保留为产品规则和开发依据。

## 1. 目标与验收口径

管理员通过 Telegram 配置执行时间和一个漫画标签。到达时间后，系统搜索该标签的漫画，优先选择点赞较高的作品，排除带 AI 生成标记的内容，去重后提交到现有下载队列，沿用 CBZ → Komga → 完成通知链路。

必须分清三个事件：计划到点、漫画入队、漫画入库完成。指定时间表示开始选书与入队，不承诺该时刻立即开始传输；现有排队、限流及网络状况会影响实际下载时间。

核心验收：同一次选书批次按可验证的点赞优先顺序入队；明确标记为 AI 生成的内容不进入自动下载；重复触发和进程重启不重复建任务；每次执行都有可解释的选择、排除和失败记录。

## 2. 范围与默认产品规则

| 项目 | 第一版规则 |
| --- | --- |
| 管理权限 | 仅当前配置中的 Telegram 管理员，且仅私聊 |
| 标签 | 每条计划一个必选标签；多标签用多条计划，暂不支持 AND/OR 查询语法 |
| 时间类型 | 单次指定日期时间、每天指定时间、每周指定星期和时间 |
| 时区 | 默认 Asia/Hong_Kong，使用 IANA 时区名称；每条计划显式保存 |
| 每次目标 | 默认最多新入队 5 部，允许 1–20 部 |
| 排序 | 优先使用验证过的上游“点赞降序”，不是浏览量、收藏量或综合热度 |
| AI 排除 | 自动任务强制开启，管理员不能通过聊天关闭 |
| 去重 | 已有效入库、已有活动任务、已由自动计划尝试过的作品默认跳过 |
| 超时与离线 | 不无限追补错过的执行时间；具体规则见第 7 节 |
| 启用 | 新建计划默认暂停，管理员预览并确认后启用 |
| 手动下载 | 保持现有行为；本功能的强制过滤范围为自动选书 |

这些是实现默认值，不代表用户已经指定实际标签、执行时间或下载额度。本阶段不创建真实计划、不注册外部定时任务、不运行下载。

第一版不做：自动追更、任意 cron 表达式、图像 AI 检测、后台补跑所有历史日期、多来源混合排行榜、全站穷尽排序、抢占正在下载的任务。

## 4. 上游能力核实：开发第一步

2026-10-18 阅读到的上游公开资料提供了以下线索，但不代表当前部署的 SDK 已验证：

- 官方项目 API 示例展示 `search_tag(search_query=..., order_by=...)`，并展示 `JmMagicConstants.ORDER_BY_LIKE`；示例说明 app 接口支持按点赞排序。
- 参考配置列出排序值 `mr` 为点赞降序。业务代码应使用经版本核实的 SDK 常量，不将字符串散落各处。
- 上游 `jm_entity.py` 的相册对象含 `likes`、`tags` 等字段；源码注释提示 likes 可能是 `1K`、`1W` 之类展示字符串。不能把这些字段当作精确整数。

参考来源（开发时重新核对实际 SDK 版本并保存提交号）：

- https://github.com/hect0x7/JMComic-Crawler-Python/blob/master/usage/usage_api.py
- https://github.com/hect0x7/JMComic-Crawler-Python/blob/master/assets/docs/option_file_syntax.md
- https://github.com/hect0x7/JMComic-Crawler-Python/blob/master/src/jmcomic/jm_entity.py

必须补充到 `docs/INTEGRATION_NOTES.md` 的验证结果：

1. 当前内置客户端类型是否支持标签搜索、分页和点赞排序。
2. 查询时间范围的实际默认值，能否显式固定为全时段；不支持时在结果中明确真实范围。
3. 标签搜索是否精确匹配、标签的语言和别名是否稳定；空结果、最后一页和重复页如何表示。
4. 搜索结果有哪些字段；完整详情能否区分“标签确实为空”和“字段缺失/解析失败”。
5. 点赞字段是否精确；展示缩写只能用于显示，不能伪造精确计数。
6. AI 内容实际使用的标签名称、别名、分类及明确标记；不要预设只有一种拼写。
7. 限流、超时、SDK 不支持排序时的异常，以及子进程输出大小限制。

搜索能力未核实或缺失时返回明确的 `DISCOVERY_UNSUPPORTED`，保持计划暂停。不能静默换成默认热度排序或取消 AI 排除。没有外部条件时可完成 fake provider 与离线测试，真实验收标为待完成。

## 5. 选书与排序流程

### 5.1 单次执行管线

```text
到点领取计划 → 固定规则快照与执行编号
    → 按标签、点赞降序分页搜索
    → 对来源 ID 去重，跳过已知已下载/正在处理作品
    → 查询完整详情，核对目标标签和 AI 标记
    → 固定候选顺序、排除原因和入选列表
    → 在一个事务中创建任务、写关联记录、推进本次执行状态
    → 现有 worker 下载 → CBZ → Komga → 汇总本次最终结果
```

默认每页大小使用上游支持值；最多取 10 页、200 个唯一候选、200 次详情请求或执行 10 分钟，任一预算先耗尽即停止。使用串行或低并发详情查询并尊重上游限流。分页反复返回相同 ID 时停止并报告，不无限翻页。

### 5.2 点赞优先的准确含义

排序模式按能力协商，写入每次运行记录：

- `SOURCE_LIKES_DESC`：推荐。适配器确认请求确实启用了上游点赞降序。按页号、页内位置形成稳定 rank；即使展示点赞数是缩写也保留上游顺序。逐条过滤，选前 N 个符合条件且可提交的作品。
- `EXACT_LIKES_DESC`：只有缺少可用上游排序但能获得精确点赞整数时启用。必须先收集预算内整个候选集合，再按精确点赞数降序排序；相同点赞按来源 ID 稳定排序。声明仅为“本次候选范围内点赞优先”。未知点赞不填 0，排除并计数。
- 两种模式均不可用：本次失败，禁止自动降级为浏览量、收藏数或默认搜索顺序。

不要根据 `1K` 推断恰好 1000 点赞；保存 `likes_raw`、可空的 `likes_exact`、排序模式和来源 rank。多个详情请求并发返回时仍按源 rank 组装，不按响应完成顺序选书。

上游排序可能随时间变化、分页也未必具有快照一致性，因此只承诺“按本次观察到的点赞顺序优先”。记录查询时刻和候选范围，不宣称全站绝对 Top N。

### 5.3 标签核对

搜索关键词与详情标签必须核对，不能仅因标题出现某词就判定满足目标标签。标签先做 Unicode NFKC、首尾去空白、内部空白折叠及大小写归一化；按归一化标签精确匹配。多字标签整体保存，不能按空格拆成多个标签。

只有经过验证的上游标签别名可等价匹配；别名不明时跳过并记录 `TARGET_TAG_UNCONFIRMED`。正向匹配使用原始普通 tags 字段，不使用当前代码合并的 works/characters 字段冒充普通标签。

## 6. AI 生成内容过滤

### 6.1 必须新增独立的严格元数据模型

现有 `normalize_tags` 会把缺失或非法字段转换为空并限制数量，适合展示，不足以证明已经检查过 AI 标签。发现流程返回独立结构：

- 来源与漫画 ID、标题、普通标签、作品/人物字段、来源分类或 AI 标志。
- `metadata_complete`、字段有效性、观察时间、过滤策略版本。
- `likes_raw`、`likes_exact`、搜索 rank 和排序能力证明。
- 过滤结果 `ALLOW / BLOCK / UNKNOWN` 以及命中字段与原因码。

原始字段缺失、解析异常、字段被截断或详情请求失败都不能伪装成完整空标签。当前来源所需的必检字段由适配器契约声明；完整合法但为空的 tags 可完成 AI 检查，但正向标签核对通常仍不会通过。

### 6.2 规则与边界

- 在普通标签、分类、明确 AI 标志以及可用的作品/人物字段中检查 AI 生成标记。
- 归一化后对 `ai-generate`、`ai-generated`、`ai generate`、`ai generated`、`ai生成`、`AI生成` 的等价形式建立明确别名集合；上游确认的其他拼写追加版本化规则。
- 标题中明确出现 `AI生成`、`[AI-generated]` 等标记也作为排除依据，使用词边界/完整标记匹配。
- 不使用无边界的 `"ai" in text`，避免把普通姓名或含相同字母的词误杀；独立 `AI` 标签是否算生成标记，必须根据来源语义核实。
- 命中标记为 `BLOCK`；必检元数据无法确认时为 `UNKNOWN`；两者均不自动入队。只有 `ALLOW` 且目标标签匹配的作品可以入队。
- 输出原因码如 `AI_TAG`、`AI_TITLE`、`AI_FLAG`、`METADATA_INCOMPLETE`，保留命中的规范化标记便于排查，不储存整个敏感响应。

该策略排除“带已知 AI 生成标记的内容”，无法证明未标注作品一定非 AI。用户说明与验收不得承诺零漏检。

### 6.3 下载前再检查

候选收集后可能排队较久。自动任务在首次图片下载前必须重新取得严格详情、确认目标标签及 AI 规则；调用也要支持取消和超时。发现 AI 标记时以 `CONTENT_EXCLUDED` 结束，不下载图片；将运行条目标为过滤跳过，不作为普通网络错误重试。

恢复、自动重试及手动重试自动来源任务时保留来源和过滤策略，重新检查，不允许经 `/retry` 绕过。已发布文件不自动删除；发现不再符合策略时通知管理员，禁止继续下载新页。

## 7. 调度与时间语义

继续使用现有 app 进程中的异步循环与 SQLite，不添加宿主机 cron、Redis 或外部平台定时服务。每约 15 秒检查到期计划；正常空闲条件下开始调度的目标延迟为 30 秒内，不将其作为无条件实时保证。

- 使用 `zoneinfo` 处理计划时区、UTC 时间戳处理持久化比较。安装镜像中验证时区数据库可用；缺失时明确失败。
- 单次计划需要完整日期、时间和时区，拒绝过去时间。
- 每日和每周按本地日历计算下一次，不能简单加 86400 秒。
- DST 不存在的本地时刻跳过该次；重复时刻只执行第一次。界面明确下一次当地时间、UTC 偏移与日期。
- 持久化唯一键为 `(schedule_id, scheduled_for_utc)`，避免重复 tick、系统回拨或重启重复触发。
- 创建运行记录和推进 next_run_at 在同一短事务中完成，外部请求放在事务之外。
- 每条计划只能有一个非终态运行（含已入队等待完成的批次）。下一次到点仍在运行则记录 `OVERLAP_SKIPPED` 并推进时间，不累积任务。
- 默认错过执行宽限为 30 分钟：重启时只考虑最近一个到点时间；在宽限内补一次，之前更早的点记录跳过；超过宽限不补跑。单次计划超过宽限标记 `MISSED`，等待管理员重新安排。
- 已经领取的运行属于崩溃恢复，不受“新领取”的错过宽限限制。沿用原 run_id；候选计划已固定则继续未提交步骤，尚未固定则清除该阶段未提交候选并从头搜索。已入队的只核对结果，不重新搜索和入队。
- 来源暂时失败，运行内最多尝试 3 次，并持久化 next_attempt_at；尊重 Retry-After、退避和整体 10 分钟预算。超出预算结束并记录，不阻塞其他调度或 Bot。
- 每次触发和提交前重新核对管理员身份。拥有者不再是管理员时自动暂停计划。

暂停计划只阻止未来触发和尚未入队的批次；已入队任务继续执行。另提供取消本次运行的显式操作，对该运行创建且尚未结束的任务调用既有取消流程，不删除文件，也不取消其他用户任务。

## 8. 数据结构、事务与去重

### 8.1 持久化设计

当前 schema 为 4；实施时确认仓库最新版本，新增下一版本迁移，不能硬覆盖其他功能新增的版本。

| 表/字段 | 职责 |
| --- | --- |
| schedules | id、owner_user_id、chat_id、原始/规范标签、时间类型与本地时间、timezone、limit、enabled、revision、next_run_at、created_at/updated_at |
| schedule_runs | id、schedule_id、scheduled_for_utc、trigger_type、status、规则快照、排序模式、查询范围、下次重试时间、计数、错误摘要；定时触发唯一键 |
| schedule_run_items | run_id、source、source_id、rank、likes_raw/exact、metadata_checked_at、policy_version、decision、reason、task_id；同运行同作品唯一 |
| auto_download_claims | source、source_id、run_item_id、task_id、状态；来源和作品 ID 全局唯一，防跨计划重复自动尝试 |
| schedule_notifications | run_id、event、状态、重试次数及下次时间；运行和事件唯一 |
| tasks 扩展 | origin（manual/schedule）、schedule_run_id、内容策略版本、稳定 queue_sequence；旧任务补默认值 |

运行状态建议：`DISCOVERING → PLANNED → QUEUED → FINISHED`；分支 `EMPTY / PARTIAL / FAILED / CANCELLED / MISSED / OVERLAP_SKIPPED`。任务执行失败不等于调度发现失败：保存入队数、完成数、失败数、取消数及过滤数，最终根据关联任务聚合状态。

### 8.2 提交原子性

确认候选后使用 `BEGIN IMMEDIATE`，再次检查计划 enabled/revision、管理员身份、活动任务及全局自动 claim；按顺序创建任务、插入 claim、绑定 run_item、更新运行状态，最后一次提交。单批最多 20 个任务，事务内不请求网络或扫描文件。

不要从事务内调用会再次 BEGIN 的 `Store.submit()`；提取可接收当前连接的内部提交函数，保留原手动入口及其约束测试。

崩溃测试必须覆盖事务提交前和提交后：前者全部回滚，后者通过关联记录恢复，无“任务创建了但 run 不知道”的重复窗口。

### 8.3 下载去重策略

- 已存在活动任务：跳过，不关联或泄漏其他用户任务详情，不抢占。
- 已入库且文件存在有效：跳过；在事务外做必要核对，不能只看文件名。
- 发现文件缺失、外部修改或记录冲突：记 `NEEDS_REPAIR`，交由已有修复/手动重试流程；本功能不静默覆盖文件。
- 已存在自动 claim，包括失败或取消：默认跳过，避免每天自动重新下载同一失败作品。管理员可使用任务重试；重试保留计划来源/内容策略并更新 claim 的关联。
- 新计划与旧计划对同一作品共享去重；本功能不用于自动追更。
- 事务内出现并发冲突时跳过该项，使用已经审核的后备候选补位；没有合格后备则少于 N 部，不能跳过审核硬凑数量。

### 8.4 点赞顺序如何进入真实队列

现有 `next_task()` 仅按 created_at 排序。新增稳定递增的 queue_sequence，迁移旧任务按原 created_at/id 顺序赋值；新手动任务也获得序号。自动批次按 rank 分配连续序号，队列按序号稳定领取。

只保证同一批次中可执行任务的点赞优先顺序；不抢占已经在跑的任务，不把自动批次无限插到手动队列前。高点赞任务进入退避或磁盘暂停时，允许其他可执行任务先处理。不同计划独立排序，不跨时点强行比较点赞。

## 9. Telegram 管理交互

采用独立菜单向导，文本命令作为可选快捷入口：

| 操作 | 行为 |
| --- | --- |
| `/schedules` | 分页列出计划、标签、启停状态、时区和下一次时间 |
| `/schedule_add` | 输入一个标签 → 单次/每日/每周 → 日期/时间 → 时区 → 数量 → 配置摘要 → 保存为暂停 |
| `/schedule_preview ID` | 执行受预算约束的搜索和过滤，显示预计入选作品、排序依据和排除计数，不创建下载任务/claim |
| `/schedule_enable ID` | 展示未来执行时间与强制过滤规则，二次确认后启用 |
| `/schedule_pause ID` | 暂停未来执行，反馈已有批次是否继续 |
| `/schedule_run ID` | 显式确认后立即执行一次，仍经过全部过滤与去重，不改变正常下一次时间 |
| `/schedule_runs ID` | 查看运行历史、候选数、排除原因、入队和下载结果 |
| `/schedule_cancel_run RUN_ID` | 确认后取消该批次自建任务 |

第一版修改规则可以暂停旧计划并新建；不必马上做复杂编辑器。预览结果不作为未来下载授权快照，正式执行必须重新搜索与检查。立即执行使用一次性 token 保证重复点击只产生一个 run。

所有命令、按钮回调、向导步骤都校验私聊和管理员身份。为防越权，第一版仅计划创建者可以管理自己的计划，其他管理员只能查看聚合运行状态。向导记录绑定用户和聊天并设置过期；动态标签、标题和错误摘要进行转义及长度限制。

默认每次发送一条入队摘要和一条批次结束摘要，明示 AI 排除数、未知元数据数、重复数和预算是否用尽。EMPTY 也显示原因。通知失败仅重试通知，不重新搜索或下载。已有漫画任务完成通知可暂时保留，后续再单独优化消息数量。

## 10. 运行预算与异常处理

- 默认每条计划最多 20 个新任务；全局自动来源未结束任务上限建议 50。到上限先不搜索，记录 `BACKPRESSURE` 并在本次运行预算内等待，超预算记跳过；不无限增长队列。
- 既有磁盘阈值开关继续沿用，不能因新增功能擅自修改现有部署设置。启用向导明确显示磁盘保护是否关闭。
- SDK 图片下载后的大小限制与缺少 staging 自动清理仍是现有约束，不能因限制每次部数就宣称磁盘有严格配额。
- 搜索请求全局限并发，默认一个发现运行同时访问来源；其他到期运行记录后等待调度。不要用网络请求卡住 tick 或 Bot 主循环。
- 在候选已固定前预算耗尽可形成部分结果，但必须说明截断范围；无法证明排序或缺少严格元数据的条目不可入队。
- 调度异常应写入运行记录并继续下一条计划；持久化损坏等不可恢复错误触发明确服务失败，避免吞掉异常伪造健康。
- 日志使用 schedule_id/run_id、排序模式、数量和原因码；不记录账号凭据或完整上游响应。
- 既有同步打包可能延迟调度心跳。必须作为已知限制测量；如要求繁忙时也准点，在独立任务中解决打包隔离，避免误报调度准确性。

### S6：集成与交付

把调度服务接入 main 生命周期，更新 README、环境示例、部署说明和诊断。执行完整回归、容器内时区检查及授权小样本端到端验收；真实条件不足则准确列为未验证。不得宣称原有 80 项测试代表新增功能已经通过。

## 12. 必须验证的场景

| 类别 | 验收案例 |
| --- | --- |
| 排序 | 详情异步乱序返回不改变 rank；精确点赞 100/80/20 正确排序；缩写不冒充精确数字；不支持点赞排序明确失败 |
| 过滤 | 高点赞 AI 作品被排除；ai-generate 大小写/空白/连字符变体；AI 标题标记；普通含 ai 字母单词不误杀 |
| 元数据 | tags 缺失、异常、被截断为 UNKNOWN；合法空列表不与缺失混同；works 不冒充目标 tags |
| 候选 | 重复页、重复 ID、空页、详情失败、多个跳过后补位、预算用尽只返回审核过的部分结果 |
| 时间 | 单次、每日、每周、UTC 转换、DST 跳过/重复、时钟回拨、30 分钟边界、离线多日只处理最近一次 |
| 幂等 | 同 tick 并发领取、重复确认、跨计划同作品、事务前后崩溃、入队后重启不再搜索建任务 |
| 生命周期 | 暂停发生在搜索期间阻止提交；暂停不取消已入队；取消批次只影响自己任务；管理员被移除阻止后续执行 |
| 队列 | 同批次点赞顺序可重复验证；原手动 FIFO 保持；高点赞退避时其他任务可运行；旧任务正确迁移 |
| 再检查 | 入队后出现 AI 标记不下载；自动/手动重试继承过滤；发布文件保留并告知管理员 |
| 多用户 | 普通用户无法配置计划；旧回调和其他管理员的私有计划操作被拒绝；不泄露其他下载者 |
| 通知 | 入队不等于完成；失败、取消、入库待确认正确汇总；通知重试不重建任务 |
| 真实联调 | 在实际镜像中配置未来几分钟的单次计划，确认时区、排序、排除、任务顺序及 Komga 可读结果 |

测试素材使用虚构元数据和程序生成图片。离线测试不访问来源，真实搜索/下载作为显式启用的集成步骤。
